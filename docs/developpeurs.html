Documentation développeurs

Comprendre le code, ajouter un écran, et ne rien casser.

Démarrer

$ git clone https://github.com/aelharrak/orbisys.git
$ cd orbisys
$ cargo run --release          # interface graphique
$ cargo test                   # 347 tests
$ ./target/release/orbisys help

Prérequis : Rust 1.80 ou plus récent. Dépendances : eframe/egui 0.29, serde, serde_json, chrono, dirs. Pas de runtime asynchrone, pas de bibliothèque système autre que l'affichage (Wayland ou X11).

La version Python (main.py, PySide6) reste dans le dépôt comme référence ; la comparaison mesurée est dans docs/parite-rust-python.md.

Ligne de commande

orbisys inventory [--txt F] [--csv F] [--json F]
orbisys updates
orbisys clean [--apply]
orbisys report [DOSSIER]    # TXT, CSV, JSON et PDF
orbisys panel [NOM]         # une rubrique en texte ; sans NOM : la liste

panel est l'outil de débogage le plus utile : il exécute la collecte d'une rubrique sans interface et affiche le résultat en texte.

Architecture

Trois couches, du système vers l'écran. Les modules métier ne connaissent pas l'interface ; l'interface ne lance jamais de commande elle-même.

Interface (gui.rs, gui/panel_view.rs)egui : 39 écrans dédiés, plus un rendu unique pour les 39 rubriques génériques (tableaux, graphiques, formulaires, actions).
▲ messages (canal mpsc)
Modules métierCollecte et analyse : pkg, disk, processes, services, security, storage, network… et les rubriques génériques p_*.rs qui produisent un Panel. Les analyseurs sont des fonctions pures sur du texte, donc testables sans la machine.
▲
Exécution sûre (exec.rs, util.rs, panel.rs)Lancement de commandes sans shell, délais, élévation via pkexec, validations (noms, chemins, URL), fichiers temporaires privés.

Flux d'une action. L'interface ne bloque jamais : App::spawn lance un thread, qui renvoie un Msg par un canal ; App::poll les applique au début de chaque image. Une action risquée est d'abord stockée dans une Confirmation ; elle ne devient un Pending exécuté qu'après le clic sur « Confirmer ».

Le modèle d'écran générique

Une rubrique est une fonction fn() -> Panel. Elle décrit quoi afficher ; un seul rendu (gui/panel_view.rs) s'occupe du comment. C'est ce qui permet d'ajouter un écran sans toucher à gui.rs.

TypeContenu
PanelIndicateurs (metrics), sections, erreurs.
SectionTitre, colonnes et lignes, texte brut, note, actions globales, formulaire, graphiques.
RowCellules, drapeau « à signaler » (bad), actions propres à la ligne.
CmdUne action : programme et arguments, privileged, texte de confirm, ou une fonction interne (Cmd::local).
FormChamps de saisie et fonction build qui valide les valeurs et renvoie une Cmd ou un message d'erreur.
ChartCourbes (Lines) ou barres (Bars), unité, maximum d'axe, repères.

Exemple complet

Une rubrique qui liste les unités systemd en échec et propose de les redémarrer :

use orbisys::panel::*;

/// Analyse `systemctl --failed --plain --no-legend` : noms d'unités.
pub fn parse_failed(text: &str) -> Vec<String> {
    text.lines()
        .filter_map(|line| line.split_whitespace().next())
        .filter(|name| name.contains('.'))
        .map(str::to_string)
        .collect()
}

pub fn failed_units_from(text: &str) -> Panel {
    let mut panel = Panel::default();
    let units = parse_failed(text);
    panel.metric("En échec", units.len().to_string(),
        if units.is_empty() { Level::Ok } else { Level::Bad });

    let rows = units.iter()
        .filter(|unit| orbisys::util::valid_unit_name(unit))   // validation
        .map(|unit| {
            Row::new(&[unit.as_str()]).bad(true).action(
                Cmd::new("Redémarrer", "systemctl", &["restart", unit])
                    .privileged()                                      // via pkexec
                    .confirm(&format!("Redémarrer {unit} ?")),            // fenêtre de confirmation
            )
        })
        .collect();
    panel.section(Section::new("Unités en échec").columns(&["Unité"]).rows(rows));
    panel
}

pub fn failed_units() -> Panel {
    failed_units_from(&run_lossy("systemctl", &["--failed", "--plain", "--no-legend"]))
}

Séparer l'analyse (failed_units_from, qui prend du texte) de la collecte (failed_units, qui lance la commande) rend la rubrique testable sans la machine. Cet exemple est compilé et exécuté par tests/doc_example.rs, qui vérifie aussi qu'un nom comme --rm.service est écarté.

Les valeurs dynamiques (ici les noms d'unités) passent toujours par une validation avant d'entrer dans une Cmd : c'est la règle qui compte le plus (voir sécurité).

Ajouter une rubrique en cinq étapes

  1. Écrire la fonction dans le module p_*.rs du bon thème (ou un nouveau module déclaré dans lib.rs) : analyseurs purs d'abord, collecte ensuite, avec leurs tests.
  2. Déclarer l'identifiant dans panels.rs : une variante de PanelId, son entrée dans ALL, key() ("page.monnom"), hint_key() ("hint.monnom") et collect() (qui appelle votre fonction).
  3. Titre et conseil : deux lignes dans i18n.rs (page.monnom, hint.monnom) avec les trois langues. Le test keys_are_unique_and_translated échoue s'il en manque.
  4. Navigation : ajouter Page::Panel(PanelId::MonNom) au bon groupe de la constante NAV dans gui.rs.
  5. Traduire les libellés visibles (titres de section, colonnes, boutons, notes) dans i18n_ui.rs : la table associe le texte français à sa version anglaise et espagnole ; un texte absent reste en français.

Vérifiez ensuite sans interface avec orbisys panel monnom, puis ouvrez-la directement avec ORBISYS_PAGE=monnom cargo run. Les rubriques sont chargées à la demande, dans un thread ; PanelId::auto_refresh permet un rafraîchissement automatique (la surveillance en direct l'utilise).

Graphiques

Pas de dépendance : les courbes et barres sont dessinées avec le Painter d'egui (draw_chart dans panel_view.rs). Pour ajouter un graphique à une section :

section.chart(
    Chart::bars("Occupation (trait : 90 %)", "%",
        mounts.iter().map(|m| m.target.clone()).collect(),
        mounts.iter().map(|m| m.percent).collect())
    .max_y(100.0)
    .marks(vec![90.0; mounts.len()]),
)

Pour une courbe qui s'étend dans le temps, conservez l'historique dans une structure bornée (voir LIVE dans p_monitor.rs, un anneau protégé par un Mutex) et reconstruisez le Chart à chaque collecte.

Règles de sécurité

Une application d'administration exécute du code avec des droits élevés à partir de données qui ne sont pas toutes de confiance (noms de fichiers, sorties de commandes, fichiers de sauvegarde). Ces règles sont vérifiées par des tests ; elles sont à respecter dans toute contribution.

  1. Jamais de shell. std::process::Command avec une liste d'arguments, jamais sh -c ni concaténation. Un argument qui pourrait commencer par - est précédé de --.
  2. Valider avant d'utiliser. util::valid_package_name, valid_unit_name, panel::safe_abs_path (absolu, sans .. ni caractère de contrôle), valid_http_url, valid_username… Un nom venant d'un fichier ou d'une sortie de commande est aussi une entrée non fiable.
  3. Élévation par Polkit seulement. exec::run_privileged ou Cmd::privileged() ; jamais de sudo ni de mot de passe manipulé par le code.
  4. Confirmer ce qui détruit. Toute action destructrice porte un confirm(…) qui dit ce qui va se passer.
  5. Revérifier au moment d'agir. L'état affiché peut être périmé : un numéro de ligne ou de règle (sed -i Nd, ufw delete N), un PID réattribué, un disque remplacé. Les actions correspondantes relisent l'état et refusent si rien ne correspond (processes::check_target, edit_source_line, write_image).
  6. Fichiers temporaires privés. Ce qu'une commande privilégiée copiera ensuite passe par util::write_private_temp : dossier en 0700, création exclusive en 0600, nom unique. Jamais un nom prévisible dans /tmp.
  7. Secrets hors des arguments. Les arguments sont lisibles par tous via /proc/<pid>/cmdline : une URL à jeton ou un mot de passe passe par l'entrée standard (ex. curl -K -), et le fichier qui la stocke est en 0600 (panel::save_json).
  8. Ne jamais suivre un lien symbolique dans une suppression ou une restauration : symlink_metadata, pas metadata ; remove_dir_all sur un lien supprime le lien.
  9. Neutraliser le texte affiché : panel::strip_controls remplace les séquences d'échappement de terminal dans le rendu en ligne de commande.
  10. Lecture seule par défaut. Un écran d'analyse ne modifie rien ; une réponse (quarantaine, arrêt) est toujours une action explicite.
Précision utile : util::path_within compare des chemins lexicalement et ne résout pas les liens symboliques. Pour une garantie sur le disque, utilisez canonicalize (comme manual::remove pour /opt) ou testez chaque composant.

Un audit de sécurité du code a été mené ; ses constats (fichiers temporaires prévisibles, URL de webhook dans les arguments, archives, états périmés) sont corrigés et couverts par des tests.

Tests

CommandeCe qu'elle vérifie
cargo test347 tests : analyseurs sur des sorties d'exemple, validations (y compris les entrées hostiles), actions réelles sur des processus et fichiers de test (signaux, quarantaine, extraction), traductions.
cargo clippy --all-targetsAucun nouvel avertissement dans le code modifié.
./parity.shLes compteurs (paquets, snap, flatpak…) sont identiques à la version Python et à la vérité terrain.
./distro-test.sh [image…]Le binaire statique (musl) tourne sans plantage dans des conteneurs : Debian, Ubuntu, Arch, Fedora, openSUSE, Alpine.

Conventions de test

  • Chaque analyseur a un test sur une sortie réelle ou fidèle de l'outil, y compris ses cas limites (ligne vide, champ manquant, échappements).
  • Chaque validation a un test qui lui envoie des entrées hostiles (../, ;, retour à la ligne, -option).
  • Pour une action qui modifie le disque ou un processus, un test l'exécute pour de vrai sur un fichier ou un processus de test créé dans std::env::temp_dir().
  • Les parseurs ne dépendent pas de la langue du système : pas de mot d'en-tête anglais pour reconnaître une sortie (voir pièges).

Traductions

L'interface comme le site existent en 11 langues : anglais, français, allemand, espagnol, portugais, italien, néerlandais, japonais, coréen, chinois et arabe. La langue source est le français. Le site est traduit à 100 %. Dans l'application, les libellés des rubriques génériques et des écrans dédiés sont traduits dans les huit langues à fichier ; les valeurs dynamiques produites par le système (sorties de commandes, messages d'erreur détaillés) ne sont pas toutes traduites : elles s'affichent telles que le système les fournit.

L'application

  • i18n.rs : table (clé, fr, en, es) pour la navigation, les titres de page et les conseils. Les autres langues sont des fichiers src/lang/<code>.tsv (clé, tabulation, texte) : navigation, titres des 77 écrans, conseils (hint.*) et textes de l'interface y sont traduits. Le test file_languages_cover_every_key vérifie qu'aucune clé de la table ne manque dans une langue.
  • i18n_ui.rs : table (français, anglais, espagnol) appliquée à l'affichage des libellés des rubriques génériques. La correspondance est exacte : les textes qui contiennent une valeur variable restent en français ; les langues sans table propre utilisent l'anglais.
  • Polices. La police d'egui ne couvre ni le CJK ni l'arabe : gui/ui_fonts.rs cherche une police déjà installée (Noto Sans CJK, DejaVu Sans, Noto Naskh…) et l'ajoute en secours ; l'écran « À propos » indique quoi installer si elle manque (fonts-noto-cjk, fonts-dejavu).
  • Arabe. egui ne relie pas les lettres et n'inverse pas le sens d'écriture : arabic.rs met le texte en forme visuelle (formes contextuelles, ligatures lam-alif, ordre inversé, segments latins conservés) une fois, au chargement. La disposition de l'interface n'est pas inversée (menu à gauche).

Le site

Un dictionnaire par langue dans docs/assets/i18n/, appliqué par assets/lang.js (voir le README.md de ce dossier). python3 docs/tools/check-i18n.py mesure la couverture et signale les clés devenues obsolètes.

Ajouter une langue : un fichier .tsv et une variante de Lang pour l'application ; un dictionnaire et une entrée de LANGS pour le site.

Captures d'écran

Les captures de ce site sont de vraies captures, produites par script (tools/screenshots.py). L'application est lancée sous X11 (WINIT_UNIX_BACKEND=x11) avec ORBISYS_PAGE, …_THEME et …_LANG, puis la fenêtre est capturée avec ImageMagick.

$ cargo build --release
$ python3 tools/screenshots.py dashboard processes scan   # sans argument : toutes
Avant de publier une capture, relisez-la : elle montre les processus, chemins, noms d'utilisateur et paquets de la machine qui l'a produite.

Pièges connus

Des erreurs déjà rencontrées, pour ne pas les refaire.

  • Parsing dépendant de la langue. disk::mounts reconnaissait l'en-tête de df par le mot « Filesystem » ; sur un système en français l'en-tête est « Sys. de fichiers », la lecture retombait sur un repli qui listait 75 montages au lieu de 3. Ne reconnaissez pas une sortie par un mot localisé.
  • Paquets en état rc. dpkg-query -W liste aussi les paquets désinstallés dont la configuration subsiste : filtrez sur l'état ii (305 faux logiciels sur la machine de test).
  • PID réattribué. Entre l'affichage d'une liste et un clic, un PID peut désigner un autre processus. Comparez le nom avant d'agir ; dans un test, attendez la fin du exec du processus créé (nom et ligne de commande sont vides un instant).
  • Glyphes absents. La police par défaut d'egui n'a pas les caractères de blocs Unicode (▁▂▃) : ils s'affichent en carrés. Dessinez avec le Painter.
  • add_sized centre le contenu et allocate_ui_with_layout ne réserve que la place utilisée : pour une colonne alignée à gauche de largeur fixe, utilisez left_cell (réserve la cellule puis y place le widget).
  • Lectures réservées. Sans droits administrateur, /proc/<pid>/exe des autres utilisateurs, ufw status, /sys/kernel/security/apparmor sont illisibles : traitez « illisible » comme un état, pas comme « absent ».
  • Un conteneur n'est pas une machine. Il n'a ni ss, ni systemd, ni écran : distro-test.sh prouve l'absence de plantage, pas l'exactitude des résultats.

Contribuer

  1. Ouvrez un ticket (ou commentez-en un) pour dire ce que vous voulez faire.
  2. Créez une branche, écrivez les tests avec le code, puis vérifiez cargo test, cargo clippy --all-targets et, si vous touchez aux paquets, ./parity.sh.
  3. Si votre changement agit sur le système, suivez les règles de sécurité et décrivez dans la demande ce que vous avez validé.
  4. Décrivez la distribution sur laquelle vous avez essayé ; ./distro-test.sh pour les autres.
